# Work Plan: 物語の整合性の強化

Date: 2026-11-18

## Goal

章をまたいで設定、呼称、時系列、伏線が食い違わない小説を生成できるようにする。対象は LLM に渡すプロンプトと、その材料を作って保持する仕組み（章立て、記憶、検査）。モデルの入れ替えと UI の全面改修は対象外。

## 現状と問題

現在の流れは「あらすじ → 章立て（1 回の呼び出し）→ 各章の本文」。本文の生成が受け取るのは、章立ての全概要、直前 2 章の本文、その章の登場人物の設定。

`prisma/seed.sql` に残っている生成結果（「かぐやの学園生活」3 章、`gemini-3.1-flash-lite`）とコードから確認した問題。

| # | 問題 | 根拠 |
|---|---|---|
| 1 | 本文が決めた事実を保持しない | 直前 2 章しか渡さない (`chapter-payload.ts:151`)。第 3 章が決めた「黒いウィッグとカラコンで登校」は、章が続けば第 6 章以降に届かない |
| 2 | 章立てが計画になっていない | 概要が一人称の宣伝文調で、出来事と章末の状況が決まっていない |
| 3 | 章の境界を指示していない | 初回生成の第 1・2 章に同じ場面（因数分解の共通因数）。最新版の第 1・3 章が同じ締め句（「私は確信〜」「まだ始まったばかり」） |
| 4 | 上流の変更が下流に伝わらない | 章立ての手動編集は本文に触れない (`app.ts:413`)。途中の章を再生成しても後続は古いまま |
| 5 | 呼称と年齢の読み替えを毎回解釈させる | 「名前」「苗字＋さん」が記号のまま入る (`gemini/client.ts:213`)。彩葉からかぐやへの二人称が版によって「君」「あんた」 |
| 6 | 登場人物の取りこぼし | 完全一致しない名前を黙って捨てる (`gemini/client.ts:351`)。その章のプロンプトから人物設定が消える |
| 7 | 検査と指示つきの書き直しがない | 再生成は同じプロンプトの振り直し |

ほかに、目標 4,000 字に対して最新版が 2,254〜2,637 字、口調の例の丸写しが 1 件、段落の字下げが版によって不統一。

## 確定した方針

1. **記憶は「全文 + 記録」の二段**。予算内なら既出の章を全文で渡す。超えた分は古い章から記録に置き換える。記録は章ごとに抽出して保存する。
2. **計画は「作品設計 → 章立て → 本文」の三段**。作品設計は作品につき 1 回作り、全章に同じものを渡す。
3. **解釈が要る値は 1 回確定して保存する**（呼称表、年齢指定に合わせた人物設定）。章ごとの呼び出しでモデルに解釈し直させない。
4. **プロンプトの組み立ては純粋関数に切り出す**。`bun test` で検証する。
5. **検索（埋め込み、Vectorize）は使わない**。上限の 30 章 × 20,000 字 = 60 万字でも、全文と記録の組み合わせで足りる。
6. **自動の書き直しループは作らない**。検査は警告の表示まで。書き直しはユーザーが指示して起動する。
7. **補助の呼び出し（作品設計、記録の抽出、検査）は `editor_model` を使う**。設定項目は増やさない。

## 既存の判断を変える箇所

| 既存の判断 | 変更 | Phase |
|---|---|---|
| DO は D1 を読まず、起動時の payload を使う (`chapter-gen-do.ts:55`) | payload は ID とモデルだけにし、実行時に D1 から組み立てる。上限設定で全文を載せると DO ストレージの 1 値 2MB に近づくため | 2 |
| その章の登場人物だけに絞る (`gemini/client.ts:550`) | 絞り込みは維持。語り手は常に含め、登場しない人物も名前と呼称の 1 行を残す | 1 |
| 章立てに視点と文体を渡す (`gemini/client.ts:312`) | 外す。概要が一人称になる原因 | 3 |
| 結末は章立てだけに渡す (`gemini/client.ts:300`) | 作品設計に結末の具体像を書き、作品設計ごと本文に渡す | 3 |
| 章立てを再生成した章は本文を全 version 削除 (`app.ts:549`) | 未決（「未決事項」の 2） | 4 |

変えないもの: `maxOutputTokens` を指定しない、thinking は既定、`notes` は章立てだけに渡す、Chapter は append-only。

- [ ] 章立ての生成コストを記録する。`generateJsonText` (`gemini/client.ts:195`) が usage も返すようにし、`ChapterGenerationCost` に `kind`（`chapter` / `outline` / `bible` / `record` / `review`、既定 `chapter`）を足す。作品単位の呼び出しは `chapter_number = 0`
- [ ] `getNovelWithChapters` (`novel/repository.ts:164`) の集計を直す。章ごとの表示は `kind = chapter` の最新だけ。補助は全行を合算して別に表示する

### Phase 1: プロンプトの直し

データモデルは変えない。

- [ ] プロンプトの組み立てを `src/lib/novel/prompts.ts` に移す。`buildOutlinePrompt`、`buildOutlineChapterPrompt`、`buildChapterPrompt` を純粋関数にし、`streamChapter` (`gemini/client.ts:523`) は組み立て済みのプロンプトを受け取るだけにする。挙動を変えない移動を先に 1 コミットで済ませる
- [ ] 役割の分離: 変わらない執筆ルールを system に、資料と今回の指示を user に分ける。Gemini は `systemInstruction`、chat は `system` ロール、responses は `instructions`。`Chapter.prompt` には両方を見出しつきで連結して保存する
- [ ] 章の境界の指示を足す
  - 前章の終わりの直後から始める
  - 既出の場面と説明を繰り返さない
  - 次章以降の出来事に入らない
  - 最終章以外は章末で物語を総括しない
- [ ] 今回の指示に、執筆済みの範囲とこれからの範囲を明記する。章立ての一覧そのものは並べ替えない（Phase 2 でプロンプトの前半を固定するため）
- [ ] 「直前の章の本文（参考）」(`gemini/client.ts:573`) を「確定済みの本文」に変える。事実、呼称、時系列を矛盾させない、章立てと食い違う場合は本文を正とする、と明記する
- [ ] 「口調の例」は語尾と調子の参考で、文をそのまま使わないと添える (`gemini/client.ts:245`)
- [ ] 表記の規則を明記する（段落頭は全角 1 字下げ、会話文は字下げなし、感嘆符と疑問符の後は全角空白、三点リーダとダッシュは 2 つ重ね）
- [ ] 分量の指示を場面数に変える。目標字数から場面数（目標 ÷ 1,000、2〜8）と 1 場面あたりの字数を出して指示する
- [ ] 登場人物の正規化 (`gemini/client.ts:351`): 完全一致、次に名簿のちょうど 1 人と部分一致するものを救済、残りは捨てる。捨てた名前は応答に含めて画面に出す
- [ ] 章立ての構造化出力: Gemini は `generationConfig.responseFormat` にスキーマを渡し、`characters` を名簿の enum に限定する（`responseSchema` は非推奨）。OpenAI 互換は `json_object` のまま、コード側の検証で受ける
- [ ] 章立ての検証 (`app.ts:398`): 章数、章番号が 1 からの連番、題と概要が空でないこと。失敗したら 1 回だけ再試行し、それでも通らなければエラーを返す
- [ ] 語り手 (`pov_character_id`) を各章の登場人物に必ず含める。登場しない人物は名前、役割、呼称の 1 行だけ残す（名前だけ出る場面で呼称を間違えないため）
- [ ] 章立ての手動編集で登場人物を直せるようにする (`OutlineView.tsx:165`)
- [ ] テスト: `tests/novel-prompts.test.ts`、`tests/novel-checks.test.ts`

検証: A と B を再生成して Phase 0 の指標を比べる。目安は、章末の重複 0 件、口調の例の丸写し 0 件、字下げが全章で統一、文字数が目標の 80% 以上。届かなければ指示を調整する。

### Phase 2: 記憶

- [ ] `StartChapterGenPayload` (`chapter-gen-do.ts:57`) を `novelId`、`chapterNumber`、`model` だけにする。`runInner` (`chapter-gen-do.ts:309`) の冒頭で D1 から文脈を組み立てる。`advanceGenerationJob` (`chapter-gen-do.ts:571`) が既に DO から `buildChapterPayload` を呼んでいるので、同じ経路に寄せる。DO ストレージに残る旧形式の payload も同じ 3 項目を含むので、そのまま読める
- [ ] 既出の章の選び方 (`chapter-payload.ts:151`): 番号順に全章を全文で入れる。予算を超えたら古い章から記録に置き換える。直前 2 章は必ず全文
- [ ] 予算: 文字数 × 換算係数で見積もる。係数は Gemini が 0.65（シードの実測）、OpenAI 互換が 1.0（未実測なので安全側）。上限は 120,000 トークンで、`contextWindow` が分かるモデルはその半分との小さい方
- [ ] `Chapter.record String?`（JSON、version ごとに 1:1）を足す。`src/schemas/novel.dto.ts` に `ChapterRecordSchema`
  - `summary`: 実際に起きたこと（300 字程度、三人称の常体）
  - `facts`: 新しく確定した事実（外見、持ち物、約束、場所、日付）
  - `character_states`: 人物ごとの章末の状態（居場所、知っていること、関係の変化）
  - `threads_opened` / `threads_resolved`: 張った伏線と回収した伏線
  - `end_state`: 章末の時刻、場所、その場にいる人物
- [ ] 抽出: `runInner` で `saveChapter` の後、`advanceGenerationJob` の前に `editor_model` で 1 回呼ぶ。入力はその章の本文と、未回収の伏線の一覧（ID つき）。回収は ID で答えさせ、新規の ID はコードが振る。タイムアウトは 60 秒。失敗しても章は完了扱いにし、`record` は null のままにする
- [ ] 抽出中も `lastProgressAt` を更新する（stale 判定で再起動されないように）
- [ ] 記録が無い章（抽出の失敗、この機能より前の章）を記録として使う必要が出たら、その場で抽出して保存する。既存データの一括変換はしない
- [ ] 累積の「確定事項」をコードで組み立てる（`src/lib/novel/ledger.ts`、純粋関数）。事実は章順に連結、人物の状態は最新、伏線は張ったものから回収済みを引く
- [ ] プロンプトの並び: 変わらない資料（設定、文体、章立て）→ 既出の本文（番号順）→ 確定事項 → 今回の登場人物 → 今回の指示。章が進んでも前半が変わらないので、Gemini の暗黙キャッシュに乗りやすい。対象モデルと割引は実装時に公式ドキュメントで確認する
- [ ] 章ページに記録を表示する（プロンプト表示と同じ並び）
- [ ] テスト: `tests/novel-ledger.test.ts`、予算による選び方

検証: B で「前半の章で決まり、章立てに無い事実」を 3 つ選び、後半の章で保たれているかを読む。あわせて「全文のみ」と「全文 + 確定事項」を比べる。確定事項の上乗せ効果は未測定なので、差が無ければ確定事項は予算超過時と Phase 5 の検査だけに使う。

### Phase 3: 計画

- [ ] `Novel.bible String?`（JSON）を足す。`StoryBibleSchema`
  - `premise`: 物語の核（誰が何を求め、何が妨げるか）
  - `ending`: 結末の具体像（`ending` の方向に沿って、最終章で何が起きるか）
  - `arcs`: 人物ごとの変化（始まりの状態と終わりの状態）
  - `world`: 世界のルールと用語（表記を固定する固有名詞を含む）
  - `timeline`: 物語内の時系列（期間、季節、章と日付の対応）
  - `addresses`: 呼称表（誰が誰を何と呼ぶか、具体的な文字列）
  - `cast`: 年齢指定に合わせた人物設定（R15 と R18 のときだけ）
- [ ] 作品設計の API: 生成は `POST /api/novels/:id/bible`、手動編集は `PUT /api/novels/:id/bible`。章立ての生成は作品設計を入力に取り、無ければ先に作る
- [ ] `OutlineChapterSchema` (`novel.dto.ts:285`) を拡張する。すべて既定値つきで、旧データはそのまま読める
  - `events`: 出来事（3〜6 個）
  - `time_place`: 時と場所
  - `end_state`: 章末の状況
  - `setups`: 張る伏線（ID つき）
  - `payoffs`: 回収する伏線（ID）
  - `summary` は表示用に残し、三人称の常体と指定する
- [ ] 章立てのプロンプトから視点と文体を外す (`gemini/client.ts:312`)。年齢指定と結末は残す
- [ ] 伏線の検証: `payoffs` の ID がそれより前の章の `setups` にあること。回収されない伏線は警告として画面に出す
- [ ] 呼称表: 関係の `address_override` と人物の `address_others` を入力に、具体的な呼び方へ解決させる。関係を定義した組は必須。本文プロンプトは「他者の呼び方」(`gemini/client.ts:213`) の代わりに呼称表を渡す
- [ ] 年齢指定: R15 と R18 では、年齢、職業、外見、背景を作品設計の `cast` の文面に差し替え、辞典の原文は渡さない（口調の例と一人称は辞典のまま）。「全員 18 歳以上」の指示は残す。確定した年齢が数値で 18 未満なら、生成を始めずエラーにする
- [ ] 本文プロンプトに今回の章の `events`、`time_place`、`end_state`、伏線を渡す。分量は出来事ごとに割り当てる（Phase 1 の場面数の指示を置き換える）
- [ ] 記録の抽出（Phase 2）に、その章で張る予定と回収する予定の伏線を渡し、実際に書かれたかを答えさせる
- [ ] `Novel.writing_notes String`（本文にも渡る執筆上の指示。表記、避けたい展開）を足す。`PremiseForm` に「章立て」「本文」両方のバッジで出す
- [ ] 部分再生成 (`gemini/client.ts:393`) も同じスキーマと作品設計を使う
- [ ] 画面: 作品設計の表示と編集、章立ての新しい項目の表示と編集 (`OutlineView.tsx`)

検証: B を作り直す。概要が三人称の常体か、隣り合う章で出来事が重ならないか、呼称表どおりに呼んでいるか、文字数、を読んで確かめる。伏線の検証はコードで通ること。

### Phase 4: 下流の追従

- [ ] `Chapter` に `outline_hash String?` と `prev_chapter_id String?` を足す。生成時に、その章の章立て項目のハッシュと、直前の章として使った version の ID を保存する
- [ ] 鮮度の判定（`src/lib/novel/staleness.ts`、純粋関数）: 第 N 章は、章立て項目のハッシュが現在と一致し、`prev_chapter_id` が第 N−1 章の最新 version で、第 N−1 章も新しいときに「新しい」。値が null の章（この機能より前の章）は判定しない
- [ ] `GET /api/novels/:id` の各章に鮮度と理由を足し、章立ての一覧と章ページに「要再生成」を出す
- [ ] 生成順の検証: `POST /generation/start` (`app.ts:604`) と `POST /chapters/:number/generate` (`app.ts:564`) で、対象より前の章がすべて本文を持つか、同じバッチで先に生成されることを確かめる。満たさなければ 409。バッチは昇順に並べ直す
- [ ] 途中の章の再生成: 次章があるときは、次章の冒頭 500 字と章立て項目を渡し、そこへ繋がる状態で終えるよう指示する。後続の章の全文は渡さない
- [ ] `ChapterSelectionDialog` に「この章以降をまとめて選択」を足す
- [ ] テスト: `tests/novel-staleness.test.ts`

### Phase 5: 検査と書き直し

- [ ] コードの検査（Phase 0 の `checks.ts`）を保存時に走らせる: 文字数、登場予定の人物の出現、登場予定でない名簿の人物の出現、章末の重複
- [ ] モデルの検査: `editor_model` に本文、作品設計、確定事項、呼称表、その章の計画を渡し、矛盾を JSON で列挙させる（種別、該当箇所の引用、理由）。引用が本文に実在しない指摘はコードで捨てる
- [ ] 検査は `done` を送った後に走らせ、次章の生成を待たせない。検査中も alarm の keep-alive を続ける (`chapter-gen-do.ts:185`)
- [ ] `Chapter.review String?`（JSON）に保存し、章ページに警告として出す。検査の失敗は章の完了を妨げない
- [ ] 指示つきの書き直し: `GenerateOptionsSchema` (`novel.dto.ts:425`) に `instruction` と `base_version_id` を足す。通常の資料に加えて元の版の全文と指示を渡し、指摘箇所だけ直した全文を書かせる。結果は新しい version
- [ ] 章ページ: 警告を選んで直す操作と、自由記述の指示欄

推奨を既定として進められる。変えたい項目だけ決めればよい。

3. **作品設計の確認を必須にするか**。推奨は必須にしない。生成後そのまま章立てへ進み、編集は任意
4. **検査を毎章自動で走らせるか**。推奨は自動。記録の抽出と合わせて、章ごとに補助の呼び出しが 2 回増える

## Risks / Notes

- **入力コスト**: 4,000 字 × 30 章を目標どおりに書いた場合の、既出本文ぶんの入力だけの見積もり。換算は 0.65 トークン/字、単価は `novel.dto.ts` の表（2026-11-15 時点）。暗黙キャッシュの割引は入れていない。入力トークンは現状が約 15 万、全文が約 113 万

- **章の完了が遅くなる**: 記録の抽出は次章の開始を待たせる。思考するモデルを `editor_model` にすると長くなる
- **記録の誤りが広がる**: 抽出を誤ると後続の章に伝わる。全文が予算内にある間は全文が正で、記録は補助。記録の手動編集は Phase 2 では作らない
- **章立ての出力が大きくなる**: 章立ての生成は同期の Worker リクエスト (`app.ts:342`)。遅くなれば DO に移す
- **OpenAI 互換サーバーの差**: system ロール、JSON モード、換算係数は未実測。Phase 1 と 2 でそれぞれ 1 モデルは通す
- **コストが高めに出る**: `cachedContentTokenCount` を読まないので、暗黙キャッシュが効いた分は割り引かれない
- **旧データ**: `record`、`bible`、章立ての新しい項目が無い作品は従来どおり動く
- **実行前に確認するもの**: 開発サーバーの起動、評価のための API 利用、ローカル D1 へのマイグレーション適用
