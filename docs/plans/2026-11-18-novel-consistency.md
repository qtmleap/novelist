# Work Plan: 物語の整合性の強化

Date: 2026-11-18

## Goal

章をまたいで設定、呼称、時系列、伏線が食い違わない小説を生成できるようにする。対象は LLM に渡すプロンプトと、その材料を作って保持する仕組み（章立て、記憶、検査）。モデルの入れ替えと UI の全面改修は対象外。

## 現状と問題

現在の流れは「あらすじ → 章立て（1 回の呼び出し）→ 各章の本文」。本文の生成が受け取るのは、章立ての全概要、直前 2 章の本文、その章の登場人物の設定。

`prisma/seed.sql` に残っている生成結果（「かぐやの学園生活」3 章、`gemini-3.1-flash-lite`）とコードから確認した問題。

| # | 問題 | 根拠 |
|---|---|---|
| 1 | 本文が決めた事実を保持しない | 直前 2 章しか渡さない (`chapter-payload.ts:151`)。第 3 章が決めた「黒いウィッグとカラコンで登校」は、章が続けば第 6 章以降に届かない |
| 2 | 章立てが計画になっていない | 概要が一人称の宣伝文調で、出来事と章末の状況が決まっていない |
| 3 | 章の境界を指示していない | 初回生成の第 1・2 章に同じ場面（因数分解の共通因数）。最新版の第 1・3 章が同じ締め句（「私は確信〜」「まだ始まったばかり」） |
| 4 | 上流の変更が下流に伝わらない | 章立ての手動編集は本文に触れない (`app.ts:413`)。途中の章を再生成しても後続は古いまま |
| 5 | 呼称と年齢の読み替えを毎回解釈させる | 「名前」「苗字＋さん」が記号のまま入る (`gemini/client.ts:213`)。彩葉からかぐやへの二人称が版によって「君」「あんた」 |
| 6 | 登場人物の取りこぼし | 完全一致しない名前を黙って捨てる (`gemini/client.ts:351`)。その章のプロンプトから人物設定が消える |
| 7 | 検査と指示つきの書き直しがない | 再生成は同じプロンプトの振り直し |

ほかに、目標 4,000 字に対して最新版が 2,254〜2,637 字、口調の例の丸写しが 1 件、段落の字下げが版によって不統一。

## 確定した方針

1. **記憶は「全文 + 記録」の二段**。予算内なら既出の章を全文で渡す。超えた分は古い章から記録に置き換える。記録は章ごとに抽出して保存する。
2. **計画は「作品設計 → 章立て → 本文」の三段**。作品設計は作品につき 1 回作り、全章に同じものを渡す。
3. **解釈が要る値は 1 回確定して保存する**（呼称表、年齢指定に合わせた人物設定）。章ごとの呼び出しでモデルに解釈し直させない。
4. **プロンプトの組み立ては純粋関数に切り出す**。`bun test` で検証する。
5. **検索（埋め込み、Vectorize）は使わない**。上限の 30 章 × 20,000 字 = 60 万字でも、全文と記録の組み合わせで足りる。
6. **自動の書き直しループは作らない**。検査は警告の表示まで。書き直しはユーザーが指示して起動する。
7. **補助の呼び出し（作品設計、記録の抽出、検査）は `editor_model` を使う**。設定項目は増やさない。

## 既存の判断を変える箇所

| 既存の判断 | 変更 | Phase |
|---|---|---|
| DO は D1 を読まず、起動時の payload を使う (`chapter-gen-do.ts:55`) | payload は ID とモデルだけにし、実行時に D1 から組み立てる。上限設定で全文を載せると DO ストレージの 1 値 2MB に近づくため | 2 |
| その章の登場人物だけに絞る (`gemini/client.ts:550`) | 絞り込みは維持。語り手は常に含め、登場しない人物も名前と呼称の 1 行を残す | 1 |
| 章立てに視点と文体を渡す (`gemini/client.ts:312`) | 外す。概要が一人称になる原因 | 3 |
| 結末は章立てだけに渡す (`gemini/client.ts:300`) | 作品設計に結末の具体像を書き、作品設計ごと本文に渡す | 3 |
| 章立てを再生成した章は本文を全 version 削除 (`app.ts:549`) | 未決（「未決事項」の 2） | 4 |

変えないもの: `maxOutputTokens` を指定しない、thinking は既定、`notes` は章立てだけに渡す、Chapter は append-only。

## 実装の記録（2026-11-18）

ブランチ `feat/novel-consistency`。Phase 0〜5 を実装した。以下は、計画から変えた点と、実装の中で決めたこと。

### 未決事項の確定

4 つとも推奨どおりにした。

1. 入力コストの増加は許す。既出の章は予算（既定 120,000 トークン。`memory.ts` の `DEFAULT_CONTEXT_BUDGET_TOKENS`）まで全文で渡す。
2. 章立てを作り直しても本文は削除しない。「要再生成」の表示に統一した。
3. 作品設計の確認は必須にしない。章立てを最初に生成するときに自動で作る。
4. 検査は毎章自動で走らせる。

### 章の記録と確定事項（計画から変更）

記録の形を、計画の「人物の状態（自由記述）」から組み替えた。自由記述 1 本だと、累積するときに最新の章の分しか残らず、前の章で知ったことが落ちるため。

| 記録の項目 | 中身 |
|---|---|
| `summary` | この章の流れ（起きた順、300 字程度） |
| `facts` | 確定した事実。後の章まで続く変化（変装など）もここに書かせる |
| `characters[]` | 人物ごとの `actions`（したこと）、`learned`（知ったこと）、`state`（章末の状態） |
| `threads_opened` / `threads_resolved` | 張った伏線と、回収した伏線の id |
| `end_state` | 章末の時、場所、その場にいる人物 |

- 抽出は構造化出力（JSON Schema）で行う。`learned` には、その人物が本文の中で実際に見聞きしたことだけを書かせる。
- 次章以降に渡す【確定事項】は、全章の記録の累積。並びは「これまでの流れ → 事実 → 人物ごとの記録（状態、知っていること、したこと）→ 未回収の伏線 → 直前の章の終わり」。全文で渡している章の分も含めて毎回渡す。
- 1 章あたりの上限: 事実 15、人物 1 人につき「したこと」「知ったこと」各 6。【確定事項】全体は 40,000 字と予算の 4 分の 1 の小さい方まで。超えたら「したこと」を古い章から省く。数字は見積もりで、実生成で調整する。
- 食い違ったときの優先は「本文 > 確定事項 > 章立ての概要・作品設計」。
- 「知っていること」は抜粋として扱わせる（一覧に無いことを「知らない」と読ませない）。
- 予算を超えて全文を渡せない章は、【確定済みの本文】では見出しだけにし、中身は【確定事項】で読ませる。
- 保存するプロンプト（`Chapter.prompt`）は、既出の章の本文を字数だけの 1 行に置き換える。

### 作品設計と章立て

- 呼称表の範囲: 名簿が 8 人以下なら全ての組。それより多いときは、関係を定義した組と、語り手との組だけ。全ての組は人数の 2 乗で増え、26 人で保存の上限（600 行）を超えるため。欠けた組を相手の名前で埋めることはしない。
- 成人指定（R15 / R18）は、次の 4 つを重ねる。どれか 1 つで防ぎきる前提にはしていない。
  1. **作品設計の検証**: 作品設計の生成時に、全員の年齢・職業・外見・背景を成人として書き直させ、コードで確かめる。
     年齢の欄は「数字と、任意の 歳 / 才」だけを認めて 18 以上。人物設定と作品設計のほかの文面（物語の核、結末、人物の変化、世界のルール、用語、時系列、呼称表）に、
     未成年を指す語（高校生、学年の表現、女子生徒など）や 18 未満の年齢の表現が残っていれば不合格。照合の前に、見えない文字を取り除き、空白や中点を除いた文字列でも照合する。
     検証は、保存の上限に切り詰める前の応答と、整えた後の値の両方にかける。
  2. **生成を止める**: 検証を通らない作品設計では、作品設計の保存、章立ての生成とプレビュー、生成の開始、Durable Object の資料の準備で止める。
     利用者の「指示」の欄（執筆上の指示、物語に入れたいシーン、書き直しの指示）も、成人指定では語の検査で止める。
     指示の欄は書き手への直接の指示なので、外見向けの語（幼い、童顔、セーラー服、学校の制服など）も見る。
     指示つきの書き直しは、元の版の本文に語があれば止め、再生成へ案内する（下の「生成の流れ」）。
     エラーは 400 で、`invalid_bible`、`invalid_notes`、`invalid_instruction`、`invalid_base_content` のどれか。
  3. **読み替えの指示**: プロンプトでは、作品設計の有無に関係なく、資料のどこかに未成年を連想させる記述があっても成人として読み替えるよう指示する。
  4. **本文の検査**: 書き上がった本文に未成年を指す語が残っていれば、検査の警告に出す。
- 年齢指定は「全年齢」「R15」「R18」だけを保存できる。それ以外の値が保存されていた場合は、全年齢として扱う。
- あらすじと登場人物の辞典は、成人指定でも語の検査で止めない。辞典の人物を成人として読み替えて使うのが、このアプリの元からの作りのため。
- 語の検出は一覧との照合で、言い換えや一覧に無い表現は拾えない。区切りの記号を 1 字ずつ挟む書き方（「高/校/生」）、
  かなの混ぜ書き、ほかの文字体系での書き方のような、意図して避ける書き方も追っていない。相手にしているのは、モデルと利用者が普通に書く文面。
- 誤検出は残る（「8歳で両親を亡くし」「20歳まで施設で育った」「ティーン誌の編集者」など）。作品設計の作り直しや、指示の言い換えで済むので許した。
  成人の設定でよく出る言い方（「25、6歳」「1,000歳の吸血鬼」「九州男児」「学童保育」「JSエンジニア」）は通す。
- 既に書かれた章の本文に語が残っていても、後の章の生成は止めない。読み替えの指示と、本文の検査の警告で扱う。
- 作品設計を一度も作っていない成人指定の既存の作品は、コードの検証なしで、読み替えの指示だけで書く（変更前と同じ）。章立てを新しく生成すると作品設計が作られ、検証が働く。
- 章立ての各章に計画を足した: 時と場所、出来事（3〜6 個）、章末の状況、張る伏線、回収する伏線。概要は三人称の常体。章立てには視点と文体を渡さず、語り手の名前だけ渡す。
  計画が欠けた章があれば 1 回やり直し、それでも欠けていれば欠けたまま保存して警告を出す。
- 伏線: 前の章で張っていない伏線の回収は外して警告する。どの章でも回収されない伏線も警告する。本文には「まだ回収しない伏線」を章ごとに明示する。
- 作品設計は入力（あらすじ、登場人物、関係など）のハッシュを持ち、作成後に入力が変わると画面に注意を出す。自動では作り直さない。

### 生成の流れ

- Durable Object の payload は `{ novelId, chapterNumber, model }`（書き直しでは指示と元の版の id）だけ。文脈は実行時に D1 から組み立てる。
- 段階: 資料の準備 → 執筆 → 保存 → 記録の抽出 → 次章の起動 → 完了の通知 → 検査。段階は SSE で画面に知らせる。
- 本文を保存した後に DO が落ちた場合は、生成をやり直さず記録の抽出から再開する。
- 検査は完了の通知の後に走る。画面は完了後、約 4 分のあいだ結果を取り直す。検査中に DO が落ちたら、検査だけを 1 回やり直す。
  検査を始めてから 10 分を過ぎたら諦める。
- 鮮度: 各章の本文に、生成に使った章立ての項目のハッシュと、直前の章として使った版の id を記録する。章立てか前の章が変わると「要再生成」になる。
  途中の章を書き直すときは、次の章が既に書かれていればその冒頭を渡す（次の章が同じ生成の対象なら渡さない）。
- 指示つきの書き直しは、優先を「修正指示 > 元の版 > 章の計画」にした。分量は元の版と同じ程度にする。
  元の版が見つからないときは、生成を始める前に 400 `invalid_base_version` を返す。
- 書き直した版は、元の版の鮮度（章立てのハッシュと前の章の版）を引き継ぐ。「要再生成」の章を誤字直しで書き直しても、表示は消えない。
- 成人指定の書き直しは、元の版の本文に未成年を指す語があれば始めない（400 `invalid_base_content`）。「元の版をそのまま保つ」規則が、語を残す方向に働くため。
  そのため、本文の検査の `minor_term` の警告は書き直しでは直せず、画面は再生成を案内する。
  一覧に無い言い換えが元の版に残る場合に備えて、成人指定の書き直しのプロンプトでは、成人としての書き直しを「そのまま保つ」より優先させる。
- まとめて生成するときは、対象の章が全て章立てにあることを、始める前に確かめる。
- 検査は、資料との食い違いだけを本文の引用つきで最大 10 件まで挙げさせる。引用が本文に実在しない指摘は捨てる。章の計画にある出来事が本文から抜けている、という問題は見つけられない。
- SSE は、生成中 30 秒ごとにコメント行を送る。画面は再接続時に表示中の本文を空にする（サーバーが送り直すため）。
- 章立ての生成は、検証に落ちたら 1 回だけやり直す。待ち時間の上限は章数に応じて最大 600 秒。
